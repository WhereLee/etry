## 一、已确定的约束

1. **不使用 CDN。**
2. 视频字节始终由浏览器直接访问 COS，不经过应用服务器。
3. 当前示例视频只是占位，不是最终业务视频。
4. 实际视频预估时长：**10～40 分钟**。
5. 暂时不会提供其他 MP4 样本。
6. 学生主要在外网访问。
7. 云服务器只承担登录、列表、播放地址签发等 API，不传输视频。
8. 基础层已经上线：稳定 URL、COS 缓存头、播放日志、播放器复用和 Range 播放。

## 四、ffmpeg 是什么

`ffmpeg` 是一个开源的音视频处理工具集，包含：

- `ffmpeg`：转码、重封装、裁剪、切片。
- `ffprobe`：读取视频信息。

它不是一个必须部署到 Spring Boot 里的库。  
对本项目，它只用于**一次性视频预处理**。

### faststart 命令

```bash
ffmpeg -i input.mp4 -c copy -movflags +faststart output.mp4
```

含义：

- `-c copy`：不重新编码，不损失画质。
- `-movflags +faststart`：把 `moov` 索引移动到文件头。
- 文件大小基本不变。
- 生成新文件后，上传到新的 COS key。

### 下载信息

官方下载页：

```text
https://ffmpeg.org/download.html
```

Windows 便携版常见来源：

```text
https://www.gyan.dev/ffmpeg/builds/
https://github.com/BtbN/FFmpeg-Builds/releases
```

本次尝试的是 Gyan 的 essentials 便携包，约 109 MB。  
下载速度约 100 KB/s，预计需要十几分钟，已停止，不把半成品放入项目。

### 解决方式

优先顺序：

1. 在一台网络较好的机器下载便携版，解压后直接运行 `bin\ffmpeg.exe`。
2. 或使用已有 ffmpeg 的机器/同事电脑完成一次性重封装。
3. 或在服务器上临时安装 ffmpeg 处理，处理后不保留在应用运行链路中。
4. 不把 ffmpeg 加入 Java 项目依赖，也不在每次启动时调用。

处理后：

- 上传新对象。
- 设置缓存头。
- 更新数据库 `video_key`。
- 保留原对象。
- 用 `ffprobe` 或 COS Range 再验证一次 `moov` 位置。

## 五、将项目转移到服务器上是否方便

### 开发阶段

不建议把整个开发环境迁到服务器。

原因：

- 本地编辑、构建、浏览器验证更快。
- 服务器有 3 Mbps 带宽限制。
- 服务器还运行其他服务，混在一起容易互相影响。
- 调试日志、端口和凭证管理更麻烦。

### 一次性视频处理

如果只是用服务器上的 ffmpeg 做一次重封装，可能方便：

- Ubuntu 可以直接安装 ffmpeg。
- 服务器到 COS 的网络路径可能稳定。
- 适合作为一次性任务。

但要注意：

- 10～40 分钟视频可能有 49～195 MB，3 Mbps 下上传/下载都慢。
- 服务器内存和磁盘要留余量。
- 处理任务结束后应清理临时文件。
- 不要把 COS 密钥写入项目或临时脚本。

### 生产部署

服务器适合部署：

- 后端 API。
- 前端静态文件。
- Nginx/HTTPS。
- 日志和定时任务。

不适合：

- 视频缓存。
- 视频代理。
- 视频转码服务常驻。

原因仍然是 3 Mbps 带宽和共享资源。

### 结论

**项目代码继续在本地开发；服务器只用于部署和必要时的一次性处理。**  
为了 faststart 把整个项目搬到服务器上，不划算。  
如果只是临时用服务器装 ffmpeg 处理一个视频，可以作为备选，但不是首选。

## 九、未完成项说明

### 1. 真实 10～40 分钟视频验证

**为什么没做**

- 当前只有一个 3 分钟示例视频。
- 你明确暂时不提供其他 MP4。
- 用 3 分钟视频无法真实反映 40 分钟视频的拖动、缓冲、流量和失败率。

**怎么做**

1. 拿到第一个真实视频。
2. 用 `tools\prepare-video.ps1` 做 faststart。
3. 上传新 COS 对象并设置缓存头。
4. 更新数据库 `video_key`。
5. 测试：
   - 首帧
   - 拖动到 25%、50%、90%
   - 连续回看
   - 3～5 个真实用户同时播放
6. 对比 COS 流量和文件大小。

**验收**

- 拖动 2～4 秒内恢复。
- 单次完整观看流量不超过文件大小太多。
- 无持续 `STALLED` 或 `ERROR`。

### 2. 浏览器缓存和重复拖动的正式验证

**为什么没做**

- 当前内置浏览器无法读取 Network/Performance 资源条目。
- 服务端能确认 URL 复用和 `Cache-Control`，但不能可靠证明浏览器缓存命中。
- 需要 DevTools 或 Playwright 的 response 事件。

**怎么做**

1. 用 Chrome DevTools 或 Playwright 打开播放页。
2. 记录视频资源的 `transferSize`、`encodedBodySize`、`from disk cache`。
3. 执行：
   - 首次加载
   - 刷新
   - 切换课时
   - 拖回已看区间
   - 重复观看同一段
4. 对比请求次数和实际传输字节。

**验收**

- 同一 URL 的重复请求尽量命中缓存。
- 不出现每次切换都完整重新下载。

### 3. 真实 500 人播放测试

**为什么没做**

- 当前测试是单机 500/1000 个 Range 请求。

**怎么做**

1. 准备多台测试机或云压测资源。
2. 按 50、100、300、500 逐步加压。
3. 每个会话真实播放并执行拖动。
4. 记录：
   - 首帧
   - 拖动恢复
   - 卡顿率

- 500 个真实会话下没有大量 429/5xx。
- 卡顿率和首帧时间可接受。
- 这不用于决定 CDN（明确不考虑），只用于确认 COS 直连边界。

### 5. HLS 试点

**为什么没做**

- 当前只有 3 分钟视频，HLS 没有明显收益。
- 没有真实 10～40 分钟视频的拖动数据。
- HLS 需要转码、切片、播放列表和更多 COS 对象。
- 没有 CDN 时，HLS 不会自动降低总流量。

**怎么做**

1. 先用真实 40 分钟视频测试 MP4 + Range。
2. 如果拖动/卡顿明显不达标，再拿一个视频试点 HLS。
3. 先做一个码率、6 秒分段。
4. 对比：
   - 首帧
   - 拖动
   - 请求数
   - COS 流量
5. 不整体改造，验证收益后再决定。

### 6. 分段缓存

**为什么没做**

- 没有 CDN 时，分段缓存只在本机生效，无法跨用户共享。
- 当前需要先证明重复拖动/回看比例足够高。
- Service Worker 自己处理 Range 缓存复杂且容易出错。

**怎么做**

- 先完成 HLS 试点。
- 用日志统计同一学生重复观看同一视频的比例。
- 只有在“重复观看高 + HLS 已存在”时，再评估浏览器分段缓存或显式离线缓存。

### 7. 多码率版本

**为什么没做**

- 当前示例码率已经较低。
- 没有移动端流量和清晰度数据。
- 多码率会增加转码、存储和版本管理成本。

**怎么做**

- 只有手机端成本或清晰度成为主要问题时，准备 480p/720p 两个对象。
- 先做手动选择，不做自适应 HLS。
