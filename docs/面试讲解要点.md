# 面试讲解要点：学习资料商城

## 一句话定位
基于 Spring Boot 3 + Vue 3 的 K12 电子学习资料商城，复用并加固了一套**支付/退款/履约内核**，配套 RBAC 运营端与 PDF 试读/水印交付；个人项目，域名演示，不涉及真实交易。

## 简历可用条目（按 STAR 浓缩）
- 设计并实现资料商城交易闭环：购物车多商品结算 → 单订单多明细 → 支付 → **发件箱异步履约** → 权益交付，金额以分存储避免浮点误差。
- 加固退款内核：状态守卫 + 分布式锁 + 每订单唯一退款行，保证并发下「恰好一笔退款、权益恰好回收一次、订单终态一致」；以 10 线程并发集成测试佐证。
- 落地 RBAC：5 角色 / 12 权限点，`JwtAuthFilter` 每请求从库读权限实现**授予即时生效**，`@PreAuthorize` 方法级鉴权 + 统一 403。
- 资料交付：PDFBox 惰性生成演示 PDF、游客试读截页 + 试读水印、买家权益门槛下载 + 购买者水印；下载只认权益不认在售状态。
- 安全收口：CSP 等 5 项安全响应头、CORS 白名单、登录限流、弱口令校验、生产配置硬化（密钥必填、actuator 内网绑定）。
- 工程质量：Flyway V1–V23 版本化迁移、模块按域解耦（跨模块仅经 api 契约）、单测 231 / 集成 93 全绿、CI 三任务（frontend/backend/docker-build）。

## 架构亮点与「为什么」
1. **发件箱（outbox）异步履约**：支付成功与权益发放解耦，支付事务内只写 outbox，relay 异步投递发放/回收，避免长事务与跨服务不一致；集成测试显式 drain 使断言确定。
2. **退款并发安全**：唯一退款行 + 条件认领 + 状态守卫。讲解关键洞察——并发调用「成败分布」取决于线程调度，但**安全不变量与调度无关**；测试只断言不变量，而非要求所有调用都成功（曾因此修正 CI 偶发失败的过强时序前提）。
3. **RBAC 即时生效**：权限不写死在 JWT，而每请求从库读，授予/回收无需重新登录；legacy 角色列与 RBAC 授予经种子桥接，平滑演进。
4. **模块解耦**：identity/material/commerce/entitlement/operations/platform 按域划分，跨模块只经 api 包契约（如 `EntitlementQuery`），表归属登记，降低耦合。
5. **PDF 交付与水印**：试读截页降低带宽与泄露面，下载叠加购买者水印做溯源；演示资料由项目生成，零外部采购依赖。
6. **支付内核可替换**：Mock 与支付宝共用同一通知验签/查单/对账内核，`PAYMENT_PROVIDER` 切换，便于无商户凭据演示。

## 高频追问与应答
- **Q：并发退款怎么保证不重复退？** A：每订单唯一退款行（DuplicateKey 读已有）+ 分布式锁 + 状态守卫；晚到调用读到终态被合法拒绝，窗口内调用幂等返回同一笔。不变量：t_refund=1、权益 REVOKED=1、订单 REFUNDED。
- **Q：支付成功但履约失败怎么办？** A：outbox 重试（max-retry + 退避），定时对账 + 主动查单兜底，告警监控「已支付未履约」超时；运营端可人工补履约。
- **Q：权限改了要重新登录吗？** A：不用。JWT 只带身份，权限每请求从库读，授予即时生效。
- **Q：金额为什么用分？** A：避免浮点累计误差，`priceCents` 长整型存储与计算。
- **Q：下架后已购还能下载吗？** A：能。下载只认权益不认在售状态，保护已购用户权益。
- **Q：测试怎么覆盖并发？** A：`CountDownLatch + ExecutorService` 同时发起，断言安全不变量；集成测试用真实 MySQL/Redis（IT profile），非 mock 数据库。
- **Q：CI 偶发失败怎么处理？** A：定位根因（CPU 争用下的时序前提过强），修正断言到「调度无关的不变量」，而非放宽断言掩盖缺陷；保留全部安全断言。

## 已知边界（诚实陈述）
- 前端运营路由仍按 legacy 角色门控，后端按 RBAC 权限点；遗留课程模块待退役。
- 真实支付宝验收需域名/服务器/商户凭据（外部阻塞），当前以 Mock 全链路 + 集成测试佐证内核正确性。
- 本机无 Docker，容器构建由 CI docker-build 验证。
