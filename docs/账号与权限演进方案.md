# 账号与权限演进方案（btry）

更新日期：2026-11-02

## 1. 结论

当前阶段不引入完整 RBAC，保留 `t_user.role` 的单角色模型：

- `ADMIN`：管理员，负责建号、启停、重置密码、分配系列。
- `TEACHER`：讲师，通过邀请激活账号，提供教师工作台、本人系列归属校验和系列/章节/视频元数据管理。
- `STUDENT`：学员，登录后只能看到分配给自己的系列。

这个选择不是基于“数据量小”，而是基于当前只有一个明确的管理边界：管理员维护账号和学习资源，学员消费录播课。引入用户-角色-权限三张关系表后，仍需回答“谁能修改哪类资源”的具体权限矩阵；在教师端和运营端尚未定型时，先建矩阵会把未确定的业务固化。

但当前实现没有把路堵死：角色判断集中在 AOP，不在页面里散落判断；JWT 只承载用户身份和 token 版本，不把权限集合固化进长期 token；后续可以替换为权限点校验，而不需要重写登录和账号生命周期。

## 2. 当前账号规则

### 2.1 建号

- 不开放自助注册。
- 管理员创建学员账号；教师通过管理员发出的一次性邀请链接激活账号。
- 不允许通过管理接口创建第二个管理员。
- 用户名限制为 4-20 位字母、数字或下划线。
- 密码要求 8-32 位，同时包含字母和数字，并拒绝常见弱密码。
- 初始密码只使用一次；首次登录必须修改。
- 新建账号默认 `ACTIVE`，记录 `must_change_password = 1`。
- 教师邀请绑定用户名和昵称，不支持公开注册；教师激活时自行设置密码，不再强制改密。

### 2.2 首次登录与改密

- 登录成功返回 `mustChangePassword`。
- 待改密账号只能访问：
  - `PUT /api/auth/password`
  - `GET /api/auth/me`
- 其他业务接口返回 `428`，前端自动跳转改密页。
- 改密成功后增加 `token_version`，旧 token 立即失效，用户必须重新登录。

### 2.3 重置密码

- 管理员不能重置自己的密码，必须走“修改密码”。
- 重置后：
  - 密码更新；
  - `must_change_password = 1`；
  - `token_version + 1`；
  - 用户下次登录必须再次改密。

### 2.4 禁用与启用

- 管理员不能修改自己的状态，避免把自己锁在系统外。
- 禁用时立即增加 `token_version`，已签发的 token 下一次请求即被拒绝。
- 启用不会恢复旧 token；用户必须重新登录。
- 不做物理删除，保留账号、审计和系列分配关系。

### 2.5 登录保护

- 登录按“用户名 + IP”使用 Redis Lua 原子计数限流。
- 默认 10 分钟内同一用户名 + IP 最多 8 次失败。
- 同一 IP 跨用户名默认最多 40 次失败，降低撞库和用户名枚举风险。
- 只有失败才计数；成功登录清理用户名 + IP 计数。
- Redis 不可用时放行登录并记录警告，优先保证内部系统可用性。
- 只有可信反向代理场景才读取 `X-Forwarded-For` / `X-Real-IP`。

### 2.6 系列分配

- 只有学员可以分配系列。
- 保存前校验系列 ID 全部存在。
- 先完整校验，再替换 `t_student_series`，避免非法请求先删后失败。
- 学员的学习空间与系列详情均再次校验归属，不能靠前端隐藏实现授权。

## 3. 技术落点

### 3.1 JWT 与会话失效

- JWT 包含 `userId` 与 `ver`。
- 每次请求读取数据库中的账号状态和 `token_version`。
- 账号被禁用、重置密码、用户改密后，旧 token 自动失效。
- 这里优先选择“数据库状态为准”，没有把授权状态复制到 Redis；账号状态变更频率低，查询成本远低于状态不一致的风险。

### 3.2 AOP

- `@RequireRole` / `RoleAspect`：集中做接口角色校验。
- `@AdminAudit` / `AdminAuditAspect`：记录操作人、动作、目标类型、成功/失败、耗时和错误。
- `@Measured`：输出管理员接口耗时指标。
- `@RateLimit`：建号接口使用 Redis Lua 原子限流。
- `@Idempotent`：账号写操作使用 Redis 幂等键，防止双击和重试重复提交。

幂等键使用 SHA-256 哈希参数，不把密码等敏感明文写入 Redis key。业务方法抛异常时主动释放预留键，允许在失败后立即重试；释放失败则等待 TTL 自动过期。

### 3.3 Redis

账号域使用 Redis 的位置：

- 建号限流；
- 写操作幂等；
- 与视频 URL 缓存、播放限流共享现有 Redis 基础设施。

Redis 故障时，限流和幂等组件选择放行，避免辅助组件阻塞管理员操作。账号状态和 token 版本仍以 MySQL 为准。

### 3.4 MyBatis

- `AdminUserMapper` + `AdminUserMapper.xml` 负责：
  - 关键词、角色、状态筛选；
  - 分页总数；
  - 学员系列查询与替换。
- 写操作使用 `JdbcTemplate`，因为建号、状态变更、密码更新是简单且需要事务控制的单表/少表操作。
- 列表查询交给 MyBatis，保留动态 SQL 和后续扩展空间。

### 3.5 审计

审计写入 `t_admin_audit_log`，当前记录：

- 操作人；
- 动作；
- 目标类型；
- 目标用户 ID；
- 是否成功；
- 耗时；
- 错误摘要；
- traceId；
- 时间。

审计写入失败只记录应用日志，不回滚主业务，避免审计组件成为业务单点。生产环境若要求强审计，应改为同库事务或可靠消息，这一取舍需要根据合规要求决定。

## 4. 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/auth/login` | 登录，返回是否必须改密 |
| `GET` | `/api/auth/me` | 当前用户 |
| `PUT` | `/api/auth/password` | 修改自己的密码 |
| `GET` | `/api/admin/users` | 用户分页、关键词/角色/状态筛选 |
| `POST` | `/api/admin/users` | 创建学员；教师必须通过邀请注册 |
| `PUT` | `/api/admin/users/{id}/status` | 启用/禁用 |
| `PUT` | `/api/admin/users/{id}/password` | 重置密码 |
| `GET` | `/api/admin/series` | 可分配系列 |
| `GET` | `/api/admin/users/{id}/series` | 查询学员系列 |
| `PUT` | `/api/admin/users/{id}/series` | 替换学员系列 |

## 5. 数据模型

`t_user` 新增：

- `must_change_password`：是否必须先改密。
- `token_version`：会话版本，用于撤销旧 token。
- `updated_at`：最后更新时间。

`t_admin_audit_log`：管理员操作审计，包含目标用户 ID 和 traceId。

`t_student_series`：学员与系列的多对多分配关系，保留 `sort` 作为学习空间展示顺序。

## 6. 测试覆盖

后端单元测试覆盖：

- 不能禁用自己；
- 不能重置自己的密码；
- 只有学员能分配系列；
- 非法系列 ID 不会先删除现有分配；
- 禁用账号会增加 `token_version`；
- 重置密码会要求再次改密并增加 `token_version`；
- 不能创建重复用户名；
- 管理接口不能创建管理员；
- JWT 携带 token 版本；
- token 版本变化、账号禁用、待改密状态在过滤器中的处理；
- 幂等键不包含密码明文；
- 业务失败时释放幂等键。
- 登录达到阈值后返回 429；
- 登录限流 Redis 故障时放行；
- 可信代理开启时使用首个 `X-Forwarded-For`；
- traceId 写入响应头并清理 MDC；
- 播放日志记录请求 traceId；
- 安全响应头包含 CSP、nosniff 和 frame deny。

真实 HTTP 链路已验证：

1. 管理员登录并完成首次改密；
2. 创建学员；
3. 分配两个系列；
4. 学员首次登录被 `428` 拦截；
5. 学员改密后重新登录；
6. 学习空间只显示已分配的两个系列；
7. 系列详情和视频播放地址可获取；
8. 学员访问管理接口返回 `403`；
9. 禁用学员后旧 token 返回 `401`；
10. 重新启用后学员可重新登录。

## 7. 为什么现在不上 RBAC

满足以下任一条件时，再升级 RBAC：

1. 同一角色内部出现稳定、互相冲突的权限差异，例如“物理讲师只能看物理系列，英语讲师只能看英语系列”。
2. 出现多个管理边界，例如教务、运营、财务各自管理不同资源。
3. 需要按资源实例授权，而不是按角色授权，例如只允许某位讲师编辑某个系列。
4. 需要后台动态配置菜单或权限点，且改动频率足以抵消模型复杂度。
5. 需要对外部合作方开放受限账号，权限边界不能只靠三个角色表达。

如果只是 10-20 人内部使用，且管理员职责集中，单角色模型可以长期工作。RBAC 不会自动带来安全，错误的权限矩阵反而更难审计。

## 8. RBAC 迁移路径

建议按以下顺序演进，而不是一次性重写：

1. 新增 `t_role`、`t_permission`、`t_user_role`、`t_role_permission`，保留 `t_user.role` 作为兼容主角色。
2. 将现有 AOP 从“校验角色字符串”扩展为“校验权限点”，例如 `admin:user:create`、`admin:user:reset-password`。
3. 登录时仍只签发 `userId + token_version`；权限从服务端查询，避免权限变更后长期 token 仍持有旧权限。
4. Redis 缓存“用户权限集合 + 权限版本”，角色或授权变更时递增版本并使缓存失效。
5. 审计补充目标 ID 与变更前后摘要。
6. 前端菜单只做显示控制，接口权限始终由后端拦截。

迁移期间保持接口兼容：角色仍可用于首页跳转和粗粒度导航，真正授权以后端权限点为准。

## 9. 当前明确未做

- 不提供第二个管理员的创建入口。
- 不提供账号删除。
- 不提供邮件/短信找回密码。
- 不提供 MFA、设备管理、登录历史页面。
- 不提供完整 RBAC 和动态菜单。
- 不提供教师端资源管理。
- 密码策略尚未加入历史密码校验。
- 登录保护尚未加入账号级长期锁定和 MFA。

这些缺口不阻塞当前“管理员建号 → 学员登录 → 改密 → 看分配系列”的主链路。
