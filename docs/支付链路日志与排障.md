# 支付链路日志与排障

更新日期：2026-11-05

## 1. 日志位置

- 生产：`/opt/btry/logs/btry-prod.log`
- systemd stdout/stderr：`/opt/btry/logs/stdout.log`、`stderr.log`
- staging Docker：`/app/logs/btry.log`（卷 `backend-logs`）

日志格式包含 `traceId`：

```text
%5p [traceId=%X{traceId:-}]
```

生产为单实例，日志同时按 20MB 轮转、保留 14 份。

## 2. 关键日志标记

| 标记 | 触发点 | 关键字段 |
|---|---|---|
| `payment_initiate` | 发起支付/复用支付尝试 | `orderNo`、`attemptNo`、`channel`、`amountCents`、`providerTradeNo` |
| `payment_callback_verified` | 支付宝回调验签、归属校验、金额解析后 | `notifyId`、`outTradeNo`、`tradeNo`、`tradeStatus`、`amountCents`、`orderNo`、`attemptNo` |
| `payment_callback_processed` | 回调确认/幂等处理后 | `notifyId`、`orderNo`、`success`、`duplicate`、`orderStatus` |
| `payment_confirm_result` | 支付事件确认 | `eventKey`、`provider`、`tradeNo`、`amountCents`、`success`、`duplicate`、`orderStatus` |
| `payment_query_result` | 主动查单 | `status`、`providerTradeNo`、`tradeNo`、`amountCents`、`message` |
| `order_fulfilled` | 履约成功 | `orderNo`、`userId`、`seriesId` |
| `payment_refund_result` | 退款处理完成 | `refundNo`、`status`、`attemptCount`、`providerRefundNo`/`nextRetryAt` |

失败路径继续保留原有日志：

- 回调报文解析失败、验签失败
- `app_id` / `seller_id` 不匹配
- 未知订单/未知支付尝试
- 金额无法解析或金额不一致
- 支付宝下单、查单、退款异常

日志只记录订单号、支付尝试号、渠道交易号、事件号、金额和状态；**不记录私钥、签名、完整回调报文、用户敏感信息**。

## 3. 真实支付后的查法

假设订单号为 `ORD...`：

```bash
grep 'ORD...' /opt/btry/logs/btry-prod.log
grep 'payment_callback_verified' /opt/btry/logs/btry-prod.log | tail -20
grep 'payment_confirm_result' /opt/btry/logs/btry-prod.log | tail -20
grep 'payment_refund_result' /opt/btry/logs/btry-prod.log | tail -20
```

按 traceId 串联：

```bash
grep 'traceId=<traceId>' /opt/btry/logs/btry-prod.log
```

## 4. 数据库核对

```sql
SELECT order_no, status, price_cents, provider_trade_no,
       paid_at, fulfilled_at, last_error
FROM t_order
WHERE order_no = 'ORD...';

SELECT attempt_no, status, provider_trade_no, provider_status,
       provider_amount_cents, created_at, finished_at
FROM t_payment_attempt
WHERE order_id = (SELECT id FROM t_order WHERE order_no = 'ORD...');

SELECT event_key, event_type, amount_cents, process_status,
       error_message, received_at, processed_at
FROM t_payment_event
WHERE order_id = (SELECT id FROM t_order WHERE order_no = 'ORD...')
ORDER BY received_at;

SELECT refund_no, status, attempt_count, next_retry_at,
       provider_refund_no, error_message
FROM t_refund
WHERE order_id = (SELECT id FROM t_order WHERE order_no = 'ORD...');
```

## 5. 真实支付验收清单

1. 确认 `PAYMENT_PROVIDER=alipay`、`PAYMENT_MOCK_ENABLED=false`。
2. 确认 `ALIPAY_NOTIFY_URL` / `ALIPAY_RETURN_URL` 指向当前域名，HTTPS 证书有效。
3. 用最小金额发起一笔订单，记录 `orderNo`。
4. 支付完成后依次检查：
   - `payment_callback_verified`
   - `payment_callback_processed`
   - `payment_confirm_result`
   - `order_fulfilled`
   - `payment_refund_result`（如果做退款）
5. 用上面的 SQL 对照数据库状态。
6. 若回调失败，先看验签/app_id/seller_id 日志，再看支付宝侧通知记录。

## 6. 当前边界

- 日志能按订单号、事件键、traceId 定位；支付表目前没有单独的 `trace_id` 列，跨日志和数据库主要靠订单号/事件键关联。
- 不保存完整回调原文；如果后续需要证据留存，应单独做脱敏审计表，而不是把原始报文写日志。
- 打开 Prometheus/Grafana/Jaeger 后，可以把支付日志 traceId 与 Jaeger trace 对照；生产默认不启用 tracing。
