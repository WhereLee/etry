## 1. 目标

在不拆分微服务、不改变现有 API/数据库/部署方式的前提下，用稳定契约降低模块之间的直接依赖。

目标不是“多写接口”，而是：

- 业务模块只依赖其他模块公开的 `api`/`port`；
- 外部设施（Redis、COS、数据库、支付宝）通过适配器接入；
- 管理端只做编排和展示，不直接操作其他模块 Repository；
- 用测试约束依赖方向，防止架构回退。

## 2. 改造前的主要耦合

| 位置 | 直接依赖 | 问题 |
|---|---|---|
| 支付确认、退款、履约 | `AlertLogRepository` | 交易模块知道告警表结构 |
| 课程播放 | `PlaybackUrlCache`、`PlaybackLogService` | 课程模块知道 Redis/COS 缓存和日志队列 |
| 管理员订单 | `OrderRepository`、`PaymentRepository`、`PaymentService`、`RefundService`、`OrderFulfillmentService` | 运营端直接编排交易内部流程 |

第一阶段已经消除了这三类直接依赖。

## 3. 目标依赖模型

```text
Controller
  -> Application Service / Facade
    -> Domain / Repository
    -> Outbound Port
      -> Adapter（MySQL / Redis / COS / Alipay）

operations.admin
  -> commerce.api.AdminOrderOperations
  -> platform.api / platform.common
```

模块公开的契约放在各自 `api` 包；实现保留在模块内部。

## 4. 已落地契约

### 4.1 AlertPublisher

位置：`modules.platform.alert`

```text
commerce.payment
  -> AlertPublisher（端口）
    -> AlertLogPublisher（适配器）
      -> AlertLogRepository
```

支付确认、退款、履约只表达告警事实，不直接依赖告警表。以后接 webhook、邮件或告警平台时，不需要改交易服务。

### 4.2 PlaybackUrlProvider

位置：`modules.learning.api`

```text
course.series
  -> PlaybackUrlProvider
    -> CachedPlaybackUrlProvider
      -> PlaybackUrlCache
        -> COS / Redis
```

课程播放不再知道缓存实现、预签名细节和 Redis 降级逻辑。

### 4.3 PlaybackEventPublisher

位置：`modules.learning.api`

`PlaybackLogService` 实现该端口。课程模块只发布“请求了播放地址”这一事实，不依赖日志队列和持久化实现。

### 4.4 AdminOrderOperations

位置：`modules.commerce.api`

运营端订单门面提供：

- `snapshot`：订单详情、支付尝试、支付事件、退款状态；
- `queryNow`：主动查单；
- `fulfill`：补履约；
- `close`：关闭未支付订单；
- `refund`：管理员退款。

`operations.admin` 只依赖 `AdminOrderOperations`，不再直接使用订单/支付 Repository 和补偿服务。

## 5. 设计模式使用原则

- **端口与适配器**：用于 Redis、COS、告警、支付渠道、后续外部通知。
- **门面**：用于跨模块编排，尤其是管理端操作。
- **策略**：用于支付渠道和后续可替换的告警投递方式；当前 `PaymentGateway` 已具备策略形态。
- **装饰器**：用于缓存、指标、重试；不改变核心接口语义。
- **状态策略**：订单状态转换建议抽 `OrderTransitionPolicy`，但保留枚举和 SQL 条件更新，不引入经典 State 类层级。
- **领域事件**：只用于非资金副作用；资金确认和权益发放仍保持同步事务与补偿。
- **事务性 outbox**：作为后续可选项，当前不引入 MQ 和 outbox。

## 6. 事务与一致性边界

必须保持同步或可补偿的部分：

- 支付事件入库与订单支付确认；
- 权益发放；
- 退款状态与权益撤销；
- 订单状态的条件更新。

可以异步化的部分：

- 告警推送；
- 指标统计；
- 播放日志持久化；
- 后续的通知、报表、审计扩展。

不使用进程内事件替代资金核心链路，因为 Spring 事件不具备持久化和重放保证。

## 7. 测试策略

- 单元测试验证契约实现和原有业务行为；
- ArchUnit 验证模块边界；
- 现有 `mvn test` 作为回归门禁；
- 前端构建验证不因后端迁移受影响；
- 生产发布前仍需做 API 冒烟和真实支付验收。

当前 ArchUnit 规则覆盖：

- 平台层不反向依赖业务模块；
- identity/learning 不反向依赖其他业务模块；
- commerce 不依赖 operations；
- course.series 不依赖播放实现；
- operations.admin 不直接使用交易 Repository/补偿服务。
