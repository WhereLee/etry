# 视频播放调研与实施方案

> 项目：btry 学习空间  
> 调研日期：2026-11-02  
> 约束：不使用 CDN；视频字节不经过云服务器；学生主要在外网访问。

---

## 一、结论

不用 CDN，现有架构可以直接支持 100 人同时观看录播视频。

播放链路保持为：

```text
学生浏览器 ──> COS
学生浏览器 ──> 应用服务器：只请求登录、系列列表、播放地址
```

云服务器只返回很小的 JSON 接口，不传输视频字节。

需要优化的不是“增加并发上限”，而是：

1. 让视频文件具备 faststart，改善首帧和拖动。
2. 让同一个视频在有效期内复用同一个预签名 URL。
3. 设置合理的浏览器缓存头。
4. 处理预签名 URL 过期后的播放恢复。
5. 用真实流量数据验证 100 并发和成本。

## 二、官方资料调研

### 1. COS 规格与限制

来源：[腾讯云 COS 规格与限制](https://cloud.tencent.com/document/product/436/14518)

关键数据：

| 项目 | 官方默认值 |
|---|---|
| 中国大陆公有云地域，单账号单地域上下行带宽 | 各 15 Gbit/s |
| 每个存储桶默认读请求 | 30000 QPS |
| 单文件下载热点频控 | 1000 QPS |

结论：

- COS 的并发能力远高于本项目需求。
- 100 人同时播放不是 COS 的瓶颈。
- 实际限制主要在每个学生自己的网络和 COS 下行流量费用。
- 官方规格可能调整，上线前应在控制台确认账号和地域的实际配额。

### 2. 预签名 URL

来源：[腾讯云 COS 使用预签名 URL 访问 COS](https://cloud.tencent.com/document/product/436/68284)

关键结论：

- 预签名 URL 的有效期由签名时间控制。
- 有效期过期后，请求会中断。
- 重新申请签名后，需要重新执行失败的请求。
- 预签名 URL 过期后不支持断点续传。

对播放器的影响：

- 长视频播放过程中可能遇到 URL 过期。
- 播放器不能只替换 `src`，还要保存当前播放位置，重新加载后跳回原位置。

### 3. 自定义 HTTP 头

来源：[腾讯云 COS 自定义 Headers](https://cloud.tencent.com/document/product/436/13361)

关键结论：

- COS 对象支持配置 `Cache-Control`、`Content-Type`、`Content-Disposition` 等 HTTP 头。
- 修改这些头不会修改对象本身。
- `Cache-Control` 可以控制浏览器或缓存的复用时间。

本方案使用：

```text
Content-Type: video/mp4
Cache-Control: private, max-age=3600
Content-Disposition: inline
```

`private` 表示只允许浏览器本地缓存，不进入共享缓存。  
因为明确不使用 CDN，这个设置符合当前架构。

注意：`max-age` 越长，浏览器复用越好，但用户登出后本地缓存仍可能继续存在。若要求“登出后立即不能看”，需要缩短 `max-age` 或使用 `no-store`，代价是流量增加。

### 4. Range 下载

来源：

- [腾讯云 COS 下载对象](https://cloud.tencent.com/document/product/436/64285)
- [MDN HTTP Range requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)

关键结论：

- COS 支持 `Range` 请求，媒体播放器可以只请求需要的字节区间。
- 服务端支持时返回 `206 Partial Content`。
- 响应包含 `Accept-Ranges: bytes` 和 `Content-Range`。
- 拖动进度条时，播放器会请求目标位置附近的字节，而不是重新下载整个文件。

### 5. Cache-Control 语义

来源：[MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

关键结论：

- `max-age=N` 表示响应在 N 秒内可直接复用。
- `private` 只允许浏览器等私有缓存保存。
- 浏览器缓存以完整 URL 为键，因此预签名 URL 频繁变化会降低缓存复用率。

这直接说明：后端复用同一个视频的预签名 URL，是当前方案中很重要的一步。

## 三、当前视频实测

实测对象：

```text
edu/video/91/demo-real-181s.mp4
```

实测结果：

| 项目 | 数值 |
|---|---|
| 文件大小 | 14,611,976 字节 |
| 约合 | 13.94 MiB / 14.61 MB |
| 时长 | 181.133 秒 |
| 平均码率 | 0.645 Mbps |
| ETag | 与另一个测试 MP4 相同 |
| Range 请求 | 返回 206 |
| Content-Type | video/mp4 |
| Cache-Control | 未设置 |
| faststart | 否 |

平均码率计算：

```text
14,611,976 字节 × 8 ÷ 181.133 秒
= 645,358 bit/s
≈ 0.645 Mbps
```

这是平均码率，包含视频、音频和 MP4 容器开销。  
容量估算时建议按 0.7 Mbps 左右计算，覆盖网络协议和瞬时波动。

### faststart 实测

检查结果：

```text
文件头 64KB：moov=false，mdat=true
文件尾 2MB：moov=true，mdat=false
```

说明 `moov` 在文件尾部。  
播放器为了获取索引，可能需要额外读取文件尾部。当前文件不大，影响有限；但要做到更好的首帧和拖动体验，应该重新封装。

## 四、容量估算

当前视频码率约 0.65 Mbps。

100 人同时播放：

```text
100 × 0.65 Mbps = 65 Mbps
```

远低于 COS 中国大陆单账号单地域默认 15 Gbit/s。  
即使实际网络有波动，100 路视频也不是 COS 侧的瓶颈。

风险在用户端：

- 学生自己的宽带或移动网络不足。
- 同一 WiFi 下多人共享出口。
- 视频峰值码率高于平均码率。
- 拖动导致额外 Range 请求。

流量费用公式：

```text
月流量 ≈ 播放次数 × 单视频大小 × 拖动/重播系数
```

当前视频示例：

| 播放情况 | 估算流量 |
|---|---|
| 100 次完整播放 | 约 1.4 GB |
| 1000 次完整播放 | 约 14 GB |
| 100 人各看 12 节 | 约 16.8 GB |

## 五、实施方案

### 第一步：生成 faststart 视频

不覆盖原文件，生成新对象：

```text
edu/video/91/demo-real-181s-faststart-cache.mp4
```

使用无损重封装：

```bash
ffmpeg -i input.mp4 -c copy -movflags +faststart output.mp4
```

完成后：

- 保留原对象用于回滚。
- 更新数据库中的 `video_key`。
- 验证新对象仍然是 `video/mp4`，Range 返回 206。
- 验证 `moov` 已位于文件头部。

### 第二步：设置对象 HTTP 头

对新对象设置：

```text
Content-Type: video/mp4
Cache-Control: private, max-age=3600
Content-Disposition: inline
```

目标：

- 浏览器可以缓存视频片段。
- 不进入共享缓存。
- 不改变视频文件本身。

### 第三步：后端复用播放地址

增加 `PlaybackUrlCache`：

- 以 `videoKey` 为缓存键。
- 预签名 URL 有效期建议 4 小时。
- 缓存 3.5 小时。
- 剩余有效期不足 30 分钟时刷新。
- 使用 `ConcurrentHashMap`。
- 多个请求同时未命中时只生成一次 URL。

效果：

- 同一视频在有效期内返回稳定 URL。
- 浏览器更容易复用缓存。
- 不减少首次播放的 COS 流量，但减少重复播放和切课时的重复下载。

### 第四步：播放器恢复逻辑

播放器需要监听：

- `error`
- `stalled`
- `waiting`
- `seeking`
- `seeked`

URL 过期或返回 403 时：

1. 记录当前 `currentTime`。
2. 重新请求播放 URL。
3. 替换视频地址。
4. 等待 `loadedmetadata`。
5. 恢复 `currentTime`。
6. 继续播放。

不能只替换 URL 后不恢复位置，否则用户会被送回视频开头。

### 第五步：测试

#### COS 容量测试

- 100 个并发 Range 请求。
- 每个请求 1 MB。
- 记录 TTFB、总耗时、HTTP 状态。
- 目标：无 429、无 5xx、无异常超时。

#### 浏览器播放测试

- 10～20 个真实浏览器或设备同时播放。
- 每人执行：
  - 首次播放
  - 拖动到 25%
  - 拖动到 50%
  - 拖动到 90%
  - 切换到另一节课
  - 重复播放同一视频
- 记录：
  - 首帧时间
  - 拖动恢复时间
  - 卡顿次数
  - 播放失败次数
  - 浏览器缓存命中情况

### 第六步：监控

关注 COS 控制台和日志：

- 下行流量
- GET 请求数
- 429 / 5xx
- 单文件下载 QPS
- 账号和地域带宽使用率

关注前端：

- 首帧时间
- 拖动恢复时间
- `waiting` / `stalled` 次数
- URL 过期恢复次数

---

## 六、验收标准

1. 100 个并发 Range 请求无 429、无 5xx。
2. 普通外网下首次播放 2 秒内出现画面。
3. 拖动到任意位置后 2～4 秒内恢复播放。
4. URL 过期后播放器能自动恢复，不需要用户刷新页面。
5. 重复切换同一视频时，浏览器尽量命中本地缓存。
6. COS 下行流量符合估算，没有异常放大。
7. 视频字节不经过应用服务器。

---

## 七、明确不做

本次视频方案不做：

- CDN。
- 应用服务器代理视频字节。
- 应用层视频文件缓存。
- HLS 分片。
- 视频转码平台。
- DRM。

如果后续实测发现拖动明显卡顿，再单独评估 HLS；当前 3 分钟 MP4 用 faststart + Range 足够。

---

## 八、风险与注意事项

1. **平均码率不是峰值码率**：容量估算使用 0.7 Mbps 左右更稳妥。
2. **URL 缓存会延长链接复用时间**：需要根据安全要求决定是否缩短 TTL。
3. **浏览器缓存不等于永久保存**：清理缓存、隐私模式、不同浏览器都会影响命中。
4. **当前 12 个课时共用一个视频对象**：这是演示数据，真实课程视频不同，流量会按实际视频大小计算。
5. **预签名 URL 过期不支持断点续传**：必须实现重新签名和播放位置恢复。
6. **COS 配额可能调整**：上线前确认账号、地域、存储桶的实际限制。

## 九、视频播放中可能导致成本增加的特殊情况

这一节专门说明：为什么用户观看同一段视频，产生的 COS 流量可能不同。  
计费依据是 **COS 实际返回的字节数**，不是视频时长，也不是并发人数。

### 1. 反复拖动、回看、跳转

这是最容易增加成本的场景。

例如当前视频约 14.6 MB：

- 从头看到尾：大约 14.6 MB，外加少量预缓冲。
- 看 0～60 秒，再拖回 30 秒，再拖到 90 秒：会产生多次区间请求。
- 如果这些区间没有命中浏览器缓存，重叠部分会再次从 COS 下载。
- 多次请求累计后，可能超过一个完整文件的 14.6 MB。

因此，“反复拖动可能超过一个完整文件”不是理论问题，但也不是必然结果：

- 如果浏览器缓存命中，重复区间不会再次计费。
- 如果缓存未命中或缓冲被丢弃，就会再次请求。
- 跳跃后快速关闭页面，浏览器可能已经预取了一小段，流量不一定等于实际观看时长。

### 2. 预签名 URL 每次变化

浏览器缓存的键是完整 URL，包括查询参数。

当前每调用一次播放接口就生成新的预签名 URL：

- 即使视频对象相同，URL 不同，浏览器也可能把它当成新资源。
- 切换课时、刷新页面、重新进入播放页时，可能重复下载相同字节。
- 这是当前 `btry` 最值得优先修复的成本问题。

方案中的 `PlaybackUrlCache` 就是为了让同一 `videoKey` 在有效期内返回稳定 URL。

### 3. 浏览器缓存被淘汰或不可用

以下情况会让“已经缓存过”的内容再次请求：

- 浏览器磁盘缓存空间不足，旧区间被淘汰。
- 用户使用隐私模式。
- 用户清理浏览器缓存。
- 不同浏览器、不同设备之间不共享缓存。
- 手机系统和浏览器对视频 Range 的缓存策略不同。

所以“缓存过了”不等于“下次一定命中”。

### 4. 多标签页、多设备同时观看

同一个学生打开多个标签页、多个浏览器或手机与电脑同时看：

- 每个播放器维护自己的缓冲和缓存上下文。
- 容易产生重复区间请求。
- 多设备之间的浏览器缓存不共享。

### 5. 播放 URL 在播放过程中过期

COS 官方文档明确说明：

- 预签名 URL 过期后请求会中断。
- 重新申请签名后，需要重新执行失败请求。
- 不支持断点续传。

如果播放器没有恢复逻辑，URL 过期后可能：

- 重新从头加载；
- 重复请求已经看过的区间；
- 用户手动刷新，导致整段重新下载。

方案中的“记录 currentTime → 重新取 URL → 恢复位置”就是为了避免这部分浪费。

### 6. 自动预加载或预取过多

如果改成 `preload="auto"` 或主动预取多个视频：

- 用户可能还没开始看，就已经下载了大量字节。
- 多个课时预取会叠加流量。
- 后台标签页或用户快速关闭页面也可能产生无效流量。

当前方案保持：

```text
preload="metadata"
```

只加载元数据，不主动下载完整视频。

### 7. 切换课时时重复创建播放器

当前演示中 12 个课时指向同一个视频对象。

如果每次切换课时都：

- 生成新的视频元素；
- 重新设置新 URL；
- 强制重新加载播放器；

浏览器可能重新请求相同字节。

优化方式：

- 同一 `videoKey` 复用同一个稳定 URL。
- 如果切换的课时仍指向同一对象，不重建播放器，只把 `currentTime` 重置到 0。
- 只有真正换了对象或 URL 时才重新加载。

### 8. 用户反复观看同一片段

例如学生为了听懂某一节，反复回看：

- 同一段 20 秒内容看 10 次。
- 如果每次都未命中缓存，流量会明显增加。
- 如果稳定 URL 和 `Cache-Control` 生效，重复观看可能大量命中本地缓存。

### 9. 网络抖动、失败重试

以下情况会额外请求字节：

- 播放中断后自动重试。
- `stalled` / `waiting` 后重新加载。
- 网络切换导致连接断开。
- 播放器错误处理不当，反复重新请求同一区间。

方案要求：

- 只在 URL 过期或明确错误时重试。
- 重试前保留当前播放位置。
- 设置重试次数上限，避免无限重试。

### 10. `Cache-Control` 过短或缺失

如果 COS 对象没有缓存头：

- 浏览器可能不缓存，或使用很短的启发式缓存。
- 每次重新进入页面都可能重新下载。

如果 `Cache-Control` 过短：

- 缓存很快过期，重复观看仍需回源。

如果 `Cache-Control` 过长：

- 用户登出后，本地缓存可能仍能播放一段时间。
- 这是“成本”和“访问撤销”的取舍。

当前方案建议：

```text
Cache-Control: private, max-age=3600
```

如果未来要求“登出后立即不能看”，需要缩短缓存时间或使用 `no-store`，但会增加流量成本。

### 11. 视频对象被替换

如果同一个 URL 对应新视频，浏览器可能缓存旧内容，也可能因校验重新下载。

更安全的做法是：

- 视频内容变化时使用新的对象 key。
- 旧 key 保留一段时间用于回滚。
- 不要让同一个 key 指向不同内容。

这样缓存策略简单，也不会误播旧视频。

### 12. 视频文件本身的问题

当前视频不是 faststart，`moov` 在文件尾部。

影响：

- 播放器可能需要额外读取文件尾部。
- 首帧和拖动可能需要更多请求。
- 虽然当前文件只有 14.6 MB，额外流量不大，但体验会受影响。

方案中的 faststart 重封装可以减少这类额外请求。

### 13. 高峰期并发与用户网络

100 人同时播放不会压垮 COS，但以下情况会影响体验：

- 学生个人带宽不足。
- 同一 WiFi 出口拥塞。
- 移动网络切换。
- 视频峰值码率高于平均码率。

这些不是 COS 侧的成本问题，但会导致重试、缓冲和重复请求，从而间接增加流量。

---

## 十、成本控制措施

按优先级执行：

1. **稳定播放 URL**：同一个 `videoKey` 在有效期内复用同一个预签名 URL。
2. **设置 `Cache-Control`**：使用 `private, max-age=3600`，并按安全要求调整。
3. **保持 `preload="metadata"`**：禁止自动预加载完整视频。
4. **同一对象不重建播放器**：切换课时时只重置 `currentTime`。
5. **URL 过期恢复**：保存播放位置，取新 URL 后恢复，不从零开始。
6. **重试上限**：避免网络错误导致无限重复请求。
7. **视频内容更新换 key**：不要覆盖同一个对象。
8. **监控 COS 流量和 GET 请求**：按视频、按天观察异常。
9. **测试重复拖动**：专门测试 10 次来回拖动产生的实际流量。
10. **记录播放事件**：至少记录 `seeking`、`seeked`、`waiting`、`stalled`、`error`。

## 十一、成本验收口径

除了原有的播放体验验收，还要增加成本验收：

1. 同一视频在有效期内多次进入播放页，应尽量复用同一 URL。
2. 同一对象切换课时，不应无条件重复下载完整文件。
3. 拖动 10 次同一视频后，COS 流量应有上限预期，并记录实际值。
4. 预签名 URL 过期后恢复播放，不应重新从头下载。
5. 100 个并发 Range 请求无 429、无 5xx。
6. COS 下行流量与“实际播放字节”保持可解释关系，不出现异常放大。

## 十二、多方法组合方案

可以组合多种方法，但不能把所有缓存手段同时叠加。  
正确方式是分层：

```text
基础层：编码 + URL + HTTP 缓存 + 播放器行为
增强层：按真实数据启用，例如离线缓存、低码率版本
后置层：HLS、Service Worker 复杂缓存，只有数据证明需要时才做
```

### 1. 基础层：必须做，副作用最小

#### 1.1 faststart MP4

- 把 `moov` 移到文件头。
- 使用无损重封装，不降画质。
- 新对象使用新 key，不覆盖原对象。
- 解决首帧和拖动时的额外尾部读取。

#### 1.2 稳定播放 URL

- 后端按 `videoKey` 缓存预签名 URL。
- 同一视频在有效期内返回同一个 URL。
- 缓存键是 `videoKey`，不是课时 ID。
- 多个请求同时未命中时只生成一次 URL。

这是当前成本优化里收益最大的一步。浏览器缓存以完整 URL 为键，URL 一直变，缓存就很难复用。

#### 1.3 Cache-Control

建议：

```text
Cache-Control: private, max-age=3600
```

如果对象 key 永不承载不同内容，可以进一步评估：

```text
Cache-Control: private, max-age=3600, immutable
```

`immutable` 的前提是“同一个 URL 的内容永远不变”。  
本项目应通过“内容更新换新 key”来保证这个前提。

#### 1.4 播放器只加载必要数据

- 保持 `preload="metadata"`。
- 不自动预加载完整视频。
- 不主动预取下一节。
- 不在用户未点击播放时下载完整文件。

#### 1.5 同一对象不重建播放器

当前 12 个课时指向同一个对象。  
切换课时时：

- 如果 `videoKey` 相同，复用同一个 URL。
- 不强制创建新的 `<video>` 元素。
- 只把 `currentTime` 重置到 0。
- 只有真正换了对象或 URL 时才重新加载。

这样可以最大程度复用浏览器的已缓冲区间。

#### 1.6 URL 过期恢复

- 播放器记录当前 `currentTime`。
- URL 过期或 403 时重新申请 URL。
- 等 `loadedmetadata` 后恢复播放位置。
- 重试设置上限，避免无限请求。

#### 1.7 ETag / If-Range

COS 会为对象提供 ETag 和 Last-Modified。  
浏览器在续传或 Range 请求时可能使用 `If-Range`：

- 条件成立：返回 `206 Partial Content`。
- 条件不成立：返回完整资源 `200`。

因此：

- 不要用同一个 key 承载不同视频内容。
- 内容变化必须换新 key。
- 这样浏览器和 `If-Range` 才能安全复用区间，不会拼出混合文件。

参考：[MDN If-Range](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Range)

### 2. 增强层：按数据启用

这些方法不是默认必做，而是根据实际播放数据决定。

#### 2.1 显式“缓存到本地”或离线观看

适合：

- 同一批视频被同一用户反复观看。
- 用户网络较差。
- 视频文件较小，例如当前 14 MB 级别。

做法：

- 用户主动点击“缓存到本地”。
- 或完成一次完整观看后，在后台下载完整文件。
- 使用 Cache API 或 IndexedDB 保存完整 Blob。
- 后续播放直接使用本地 Blob URL，不再请求 COS。

成本取舍：

- 第一次会下载完整文件，成本高于“只看 10 秒”。
- 后续重复观看成本接近 0。
- 浏览器存储可能被清理，需要处理失效。
- 不适合大文件和存储空间紧张的手机。

因此只对“高重复观看、小文件、用户明确需要”的场景启用。

#### 2.2 低码率版本

适合：

- 手机流量用户多。
- 视频以讲解为主，不要求 1080p。
- 当前 14 MB 视频已经较低码率，暂时不需要。

做法：

- 同一视频准备 480p / 720p 两个对象。
- 前端按设备或用户选择。
- 不做自适应 HLS，避免复杂度过高。

成本取舍：

- 低码率能直接减少字节。
- 但会增加转码、存储和版本管理成本。
- 当前视频文件很小，不建议现在做。

#### 2.3 HLS 分片

适合：

- 视频变长，例如 20～60 分钟。
- 拖动体验明显变差。
- 需要按片段缓存或自适应码率。

不适合：

- 当前 3 分钟 MP4。
- 只是为了“省流量”就上 HLS。

HLS 的影响：

- 可以把视频拆成小片段，拖动时只取附近片段。
- 但会产生更多请求和更多对象。
- 没有 CDN 时，HLS 不自动降低成本；它只是改变缓存和请求粒度。
- 还会引入转码、切片、清单文件和兼容性测试。

因此 HLS 是后置选项，不是当前基础方案。

### 3. 不建议使用的方法

#### 3.1 应用服务器代理视频

不采用：

- 增加服务器带宽压力。
- 增加内存和连接数压力。
- 与当前“直接 COS”架构冲突。

#### 3.2 对所有用户默认完整预加载

不采用：

- 只看了 10 秒的用户也会消耗完整文件流量。
- 多个视频预取会放大成本。
- 移动网络用户代价更高。

#### 3.3 Service Worker 拦截 Range 请求做部分缓存

技术上可行，但不建议作为第一版：

- 需要正确处理 `Range`、`206`、`Content-Range`、`If-Range`。
- 浏览器存储配额和淘汰策略不可控。
- 实现错误会导致黑屏、重复下载或播放错乱。
- 如果要做离线缓存，优先做“完整文件 Blob 缓存”，不要自己维护分段缓存。

### 4. 组合后的推荐顺序

```text
第 1 层：faststart + 稳定 URL + Cache-Control + preload=metadata
第 2 层：同一对象复用播放器 + URL 过期恢复 + 重试上限
第 3 层：测量重复观看、拖动次数、COS 流量
第 4 层：如果重复观看高，增加显式离线缓存
第 5 层：如果视频变长且拖动差，再评估 HLS
```

不要跳过第 3 层直接上第 4、5 层。

### 5. 组合方案的效果预期

| 方法 | 主要解决 | 成本影响 | 复杂度 |
|---|---|---|---|
| faststart | 首帧、拖动 | 略减少额外读取 | 低 |
| 稳定 URL | 浏览器缓存复用 | 明显减少重复下载 | 低 |
| Cache-Control | 缓存留存 | 减少重复请求 | 低 |
| preload=metadata | 未观看先下载 | 降低无效流量 | 低 |
| 同对象复用播放器 | 切课时重复加载 | 减少重复区间 | 低 |
| URL 过期恢复 | 播放中断 | 避免从头下载 | 中 |
| 显式离线缓存 | 反复观看 | 首次增加，后续降低 | 中 |
| 低码率版本 | 移动网络、总流量 | 直接降低单次流量 | 中 |
| HLS | 长视频、拖动 | 取决于缓存命中，可能增加请求 | 高 |

### 6. 什么时候需要升级方案

出现以下情况再启用增强层：

- 单次播放实际 COS 流量经常超过文件大小的 1.3 倍。
- 同一用户反复观看同一视频的次数明显高。
- 拖动恢复时间持续超过 4 秒。
- 视频时长增加到 20 分钟以上。
- 手机端流量成本成为主要问题。
- COS 监控显示异常重复 GET 请求。

没有这些信号时，保持基础层即可。

### 7. 最终建议

当前阶段采用：

```text
faststart
+ 稳定预签名 URL
+ private, max-age=3600
+ preload=metadata
+ 同对象复用播放器
+ URL 过期恢复
+ 重试上限
+ 100 并发和重复拖动测试
```

暂不采用：

```text
CDN
服务器代理视频
默认完整预加载
Service Worker 分段缓存
HLS
低码率多版本
```

这套组合不追求“绝对零重复流量”，目标是把重复请求压到合理范围，同时保持实现简单、可观测、可回退。

### 5. 结果解释

- 100 路、300 路、500 路、1000 路都没有出现 429 或 5xx。
- 高并发下延迟上升，主要来自单台测试机的连接数、端口和本地网络，而不是 COS 返回错误。
- 这不是分布式压测，不能据此推导全国用户同时访问的真实延迟。
- 但可以确认：**当前规模下，并发不是必须上 CDN 的理由。**

### 6. 什么时候才需要 CDN

按当前视频码率和 COS 官方默认规格：

- 100 人同时播放约 65 Mbps。
- 1000 人同时播放约 650 Mbps。
- COS 中国大陆单账号单地域默认上下行各 15 Gbit/s。

因此 CDN 不应由“100 人”触发。  
更合理的触发条件是：

1. 月 COS 下行流量费用持续超过可接受范围。
2. 用户跨地区，首帧和拖动延迟明显变差。
3. 同一批视频被大量重复观看，CDN 缓存可以显著降低成本。
4. 需要更强的抗刷量、防盗链、边缘鉴权能力。
5. 实际并发接近账号或地域配额的可观比例。

结论：**先不用 CDN；用真实账单、延迟和缓存命中数据决定。**

## 十五、播放日志排查

表：`t_playback_log`

常用字段：

| 字段 | 含义 |
|---|---|
| `source` | `BACKEND` 或 `FRONTEND` |
| `event_type` | `URL_REQUEST`、`PLAY`、`PAUSE`、`SEEKING`、`SEEKED`、`WAITING`、`STALLED`、`ERROR`、`ENDED`、`URL_REFRESH`、`LOADED_METADATA`、`HIDDEN` |
| `cache_hit` | 仅后端 URL_REQUEST 使用，1 表示复用了 URL |
| `position_seconds` | 事件发生时的播放位置 |
| `duration_seconds` | 播放器报告的总时长 |
| `message` | 错误或补充信息 |
| `session_id` | 单次页面会话 ID，用于串联同一用户的一次播放 |

### 常用查询

最近错误：

```sql
SELECT id, user_id, video_id, series_id, position_seconds, message, session_id, created_at
FROM t_playback_log
WHERE event_type = 'ERROR'
ORDER BY id DESC
LIMIT 50;
```

按会话追踪：

```sql
SELECT id, source, event_type, video_id, position_seconds, cache_hit, message, created_at
FROM t_playback_log
WHERE session_id = '<session-id>'
ORDER BY id;
```

URL 缓存命中率：

```sql
SELECT cache_hit, COUNT(*) AS n
FROM t_playback_log
WHERE source = 'BACKEND' AND event_type = 'URL_REQUEST'
GROUP BY cache_hit;
```

某视频的缓冲/卡顿统计：

```sql
SELECT event_type, COUNT(*) AS n
FROM t_playback_log
WHERE video_id = <video-id>
  AND event_type IN ('WAITING', 'STALLED', 'ERROR')
GROUP BY event_type;
```

某用户最近播放行为：

```sql
SELECT id, video_id, event_type, position_seconds, message, session_id, created_at
FROM t_playback_log
WHERE user_id = <user-id>
ORDER BY id DESC
LIMIT 100;
```

日志表当前没有自动清理。后续如果数据量变大，再增加按天归档或保留期策略。
