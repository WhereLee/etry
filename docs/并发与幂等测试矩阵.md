# 并发与幂等测试矩阵

更新日期：2026-11-05

## 1. 测试环境

- 独立 schema：`btry_it`
- 独立 Redis DB：`15`
- MySQL 8.0、Redis 7
- Spring Boot 3.3.5、Java 17
- Hikari 最大连接数 24（仅测试，用于让 20 个并发线程真实排队）
- 每个场景重复 20 次，整套测试连续执行 5 轮

集成测试默认不随 `mvn test` 执行；使用 `-Pintegration` 和 `@Tag("integration")` 显式运行。

## 2. 场景与结果

| 编号 | 场景 | 断言 | 结果 |
|---|---|---|---|
| C1 | 同一 `clientRequestId` 并发创建订单（20 线程） | 只生成 1 条订单，所有调用返回同一订单 | 通过 |
| C2 | 不同 `clientRequestId` 并发创建同一课程订单 | 受 `active_key` 唯一键约束，只生成 1 条活跃订单 | 通过 |

| C4 | 同一成功回调并发 20 次 | 只生成 1 条支付事件，只发 1 次权益，订单 FULFILLED | 通过 |
| C5 | 金额不一致回调 | 订单不发货，事件 FAILED，无权益 | 通过 |
| C6 | 成功后又收到失败回调 | 订单保持 FULFILLED，不被错误回退 | 通过 |
| C7 | 同一订单并发退款（10 线程） | 只生成 1 条退款，权益只撤销一次，订单 REFUNDED | 通过 |
| C8 | 退款与履约并发 | 订单行锁串行化，最终 REFUNDED，无 ACTIVE 权益 | 通过 |

结果：11 个集成场景全部通过；连续 5 轮，共 55 次场景执行，0 失败。

## 3. 发现并修复的问题

### 3.1 订单状态可见性

`OrderService.create`、`PaymentService.pay`、`PaymentConfirmationService.confirm` 原先使用 MySQL 默认 REPEATABLE READ。并发失败方在等待唯一键/行锁后，仍可能读到旧快照，表现为“订单状态已变化”或“支付尝试不存在”。

修复：三个关键入口改为 `READ_COMMITTED`，让等待后的查询能看到胜方已提交的订单和支付尝试。

### 3.2 并发退款重复插入

`RefundService.refund` 原先把 `uk_refund_order` 的冲突直接抛给调用方。现在捕获 `DuplicateKeyException` 并返回已有退款；已有 PROCESSING 退款直接返回，不重复调用渠道。

### 3.3 退款重试状态回迁

补偿任务把退款单从 FAILED 改成 PROCESSING，但订单仍停在 REFUND_FAILED，导致 `markRefunded` 的条件更新永远不命中。现在重试时同时把订单改回 REFUNDING。

### 3.4 退款重试重复认领

`retryRefund` 原先允许 `FAILED` 和 `PROCESSING`，两个线程都可能返回 1。现在只允许 `FAILED -> PROCESSING`，并新增 `claimPendingRefund` 让卡住的 PROCESSING 退款只能被一个补偿线程认领。

### 3.5 履约与退款竞态

履约和退款原先各自读订单再更新，可能先发权益再被退款覆盖。现在两边的最终事务都用 `SELECT ... FOR UPDATE` 锁定订单行；履约在锁内重新判断状态，退款在锁内完成状态迁移和权益撤销。

## 4. 真实进程重启验证

在 staging 上创建订单 `ORD202611051810008CBAB7B7`，支付后模拟首次履约失败，订单状态为 PAID。随后执行：

```bash
sudo docker compose --env-file .env.docker restart backend
```

等待补偿任务执行后，订单变为 FULFILLED，学习空间出现课程。该验证覆盖“进程重启后补偿恢复”，不是只调用一次 reconcile 方法。

## 5. 运行方式

```bash
# 本地单元测试（不需要 Docker）
mvn test

# 云端集成测试
bash /tmp/btry-run-it.sh
```

集成测试所需环境变量：

- `IT_DB_URL`
- `IT_DB_USER`
- `IT_DB_PASSWORD`
- `IT_REDIS_HOST` / `IT_REDIS_PORT` / `IT_REDIS_PASSWORD` / `IT_REDIS_DATABASE`
- 假 COS 凭据：`COS_SECRET_ID`、`COS_SECRET_KEY`、`COS_BUCKET`、`COS_REGION`

这些值只从服务器 `.env.docker` 读取，不写入仓库。

## 6. 边界

- 当前验证是单实例、单 MySQL，不覆盖多节点分布式锁。
- 真实支付宝回调只做了单元测试；真实网关验收仍需要商户资质和真实交易。
- 集成测试进程退出时 OTel batch exporter 可能来不及发送 span；业务 span 已在长期运行的 staging 上单独验证。
