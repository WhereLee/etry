## 二、剩余耦合（五簇，带证据）

### 簇一：operations 管理台「写走端口、读直 join」（最大一簇）
- AdminOrderService：refund/fulfill/close 走 AdminOrderOperations 端口；但 page/exceptions 走 AdminOrderMapper.xml 直 join t_order+t_user。detail() 冗余：mapper.findOne 读一遍 t_order，端口 snapshot 又读一遍。
- AdminUserService：写走端口；但 page 走 AdminUserMapper join t_user+t_entitlement；seriesOptions/assignSeries 校验走 mapper.findAllSeries 直读 t_series。
- 彻底化：commerce/identity/entitlement/course 各暴露管理台读查询端口，operations 改调端口拼装，删跨表 mapper。跨表关键字搜索收口到显式登记、受守卫约束的读模型门面。

### 簇二：course 展示反复直读 t_user 与 t_learning_progress
- SeriesRepository.findForStudent/findVideos join t_user（讲师昵称）+ t_learning_progress（完成数/进度）；TeacherContentRepository、CourseCatalogDisplay、course.governance.AdminSeriesMapper 也 join t_user。
- 彻底化：identity 暴露批量取昵称读端口、learning 暴露进度查询端口，course 改调端口（列表必须批量，避免 N+1）。

### 簇三：platform 告警直读 learning 表（真架构矛盾）
- platform.alert.AlertLogRepository.countEventSince/cacheStatsSince 直读 t_playback_log。ArchUnit 明令 platform 不得依赖业务模块，故无法靠加端口解决（platform 不能调 learning.api）。
- 正解：把「读播放统计」挪给 operations.alert（可依赖 learning.api），learning 暴露统计端口，platform.AlertLogRepository 只留写 t_alert_log。属归属搬迁。

### 簇四：api 端口泄漏内部 DTO
- AdminOrderOperations 返回值直接用 commerce.order.dto.OrderDtos + commerce.payment.PaymentDtos（内部包）；AdminOrderService 也直接 import commerce.payment.PaymentDtos。端口契约应用 api 级 DTO。
- CatalogDisplayQuery.DisplayProduct 的 teacherName/chapterCount/videoCount 是课程概念渗进 commerce 契约。

### 簇五：前端跨 feature 直引
- operations/AdminOrders.vue、AdminSeries.vue 直接 import commerce/api/order；AdminTeacherInvitations.vue 引 identity/api/invitation。后端解耦了，前端这层仍跨 feature 拿别家 api。

## 三、守卫盲点
- ArchUnit 11 条里没有一条禁止 commerce→course/learning/identity 的 import。commerce 现在干净靠自觉，北极星在 import 层没焊死（只有 TableOwnershipTest 守 SQL）。
- operations→commerce 内部 DTO 也没守。
