# btry 后端工程深度优化实施计划

更新日期：2026-11-05

适用范围：btry 单体后端、MySQL、Redis、COS 直连播放。机构规模按 10～20 人设计，不把项目包装成大型互联网平台。

关联文档：

- `docs/后端岗位能力调研与btry补齐建议.md`：为什么补这些能力；
- `docs/Docker运行与云服务器验证.md`：staging 环境和端口；
- `docs/生产运维手册.md`：生产部署、备份和排障。

## 1. 结论先行

这次优化的目标不是“把简历关键词补齐”，而是用可重复的测试和数据回答四个问题：

1. 订单、支付、退款在并发和故障下会不会重复、错乱或卡死；
2. SQL 和连接池在真实数据量下是否仍然是瓶颈；
3. JVM 在持续负载下是否稳定，是否有必要调参；
4. 出问题时能否通过指标、日志和链路快速定位。

优先级建议：

| 优先级 | 项目 | 理由 | 预计投入 |
|---|---|---|---|
| P0 | 并发、幂等、故障恢复测试 | 直接涉及订单和钱，风险最高 | 1.5～2 天 |
| P0 | SQL 与索引审计 | 压测前先排除明显数据库问题 | 0.5～1 天 |
| P0 | JVM/GC 基线与负载观察 | 为压测提供解释数据，不盲目调参 | 0.5～1 天 |
| P1 | Prometheus/Grafana 面板 | 让压测和排障有可视化依据 | 0.5～1 天 |
| P1 | k6 基础压测与容量结论 | 验证控制面瓶颈，而非追求 QPS | 1～1.5 天 |
| P2 | OpenTelemetry 链路追踪 | 单服务收益有限，但外部调用排障有价值 | 1 天左右 |
| 已完成 | Docker 运行 | Compose、健康检查、独立端口已验证 | 已完成 |

如果时间只够做一件事，先做**并发/幂等/故障恢复测试**。它比加面板和加追踪更能直接降低真实资金链路的风险。

## 2. 当前基础与缺口

已有基础：

- Java 17、Spring Boot 3.3.5、MyBatis、Flyway、Redis、Resilience4j、Micrometer/Prometheus。
- 后端 40 个测试类、128 个测试通过；ArchUnit 已固化 8 条模块边界规则。
- 订单、支付尝试、支付事件、退款已有数据库唯一键：
  - `uk_order_client_request(user_id, client_request_id)`
  - `uk_order_active_key(active_key)`
  - `uk_payment_attempt_no(order_id, attempt_no)`
  - `uk_payment_provider_trade(channel, provider_trade_no)`
  - `uk_payment_event_key(provider, event_key)`
  - `uk_refund_order(order_id)`
- Docker staging 四容器健康，生产 systemd 未受影响。

主要缺口：

| 能力 | 现状 | 缺口 |
|---|---|---|
| 并发/幂等 | 有单元测试和唯一键 | 没有并发访问真实 MySQL 的集成测试 |
| 故障恢复 | 有补偿任务、Mock 故障场景 | 没有“支付中/退款中重启”的可重复验收 |
| SQL | 已有主要索引 | 没有 EXPLAIN、慢查询和扫描行数记录 |
| JVM/GC | G1、Actuator、Micrometer | 没有 GC 日志、JFR、线程和堆基线 |
| 监控 | `/actuator/prometheus` 可用 | 没有面板、没有统一看瓶颈的位置 |
| 链路 | traceId、日志、DB trace 字段 | 没有 HTTP/DB/外部调用的 span |
| 压测 | 无 | 没有阶梯压测和容量结论 |
| Docker | 已完成 | 可补可观测性 profile，不重做基础 Compose |

## 3. 总体执行顺序

建议按下面的顺序做，避免“先压测、后补测试、最后发现状态机有漏洞”：

```text
Phase 0  环境与测试夹具
Phase 1  SQL/索引审计 + 慢查询
Phase 2  并发/幂等/故障恢复
Phase 3  JVM/GC 基线与可观测性面板
Phase 4  k6 压测与容量结论
Phase 5  OpenTelemetry（可选）
Phase 6  文档、清理、复盘
```

Phase 1 和 Phase 2 可以部分并行；Phase 3 的面板要在 Phase 4 之前可用；Phase 5 不应阻塞 Phase 4。

Phase 1 放在前面是因为成本低、能快速排除明显的数据库问题；如果时间只够做一件事，直接跳到 Phase 2。

## 4. Phase 0：环境与测试夹具

### 目标

让后续测试可重复，不污染生产，不依赖人工点页面。

### 动作

- 固定 staging 环境：`/home/ubuntu/btry-staging`，独立 MySQL/Redis 容器。
- 约定测试数据：学生账号池、课程系列、订单、支付事件、退款记录。
- 新增 `reports/` 目录并加入 `.gitignore`，存放 JFR、heap dump、k6 原始结果；文档只保留摘要。
- 为集成测试增加 `integration` 标签和 Maven profile，默认 `mvn test` 不受影响。
- 优先用 Testcontainers MySQL 做隔离；如果云服务器拉镜像慢，退化为独立 staging schema，但绝不指向生产库。
- 准备一份“测试后清理”SQL：清空测试订单/支付/退款/播放日志，保留基础账号和课程。

### 交付物

- `server/src/test/java/.../integration/` 测试目录；
- `tools/test-data/` 数据准备和清理脚本；
- `docs/测试环境与数据约定.md`（可并入并发测试文档）。

### 验收

- `mvn test` 仍可在本地无 Docker 环境通过；
- 集成测试只在显式 profile 下运行；
- 测试数据可重复创建和清理，不依赖生产数据。

## 5. Phase 1：SQL 与索引审计

### 目标

在压测前确认核心查询没有全表扫描、错误排序或多余回表；不做“看到慢就加索引”的盲调。

### 优先审计的查询

| 场景 | 代码入口 | 重点 |
|---|---|---|
| 用户订单分页 | `OrderRepository.countUserOrders/findUserOrders` | `user_id + created_at`，排序是否走索引 |
| 进行中订单 | `OrderRepository.findActive` | `active_key` 唯一键是否命中 |
| 待查单订单 | `OrderRepository.findPendingQuery` | `status + updated_at` |
| 过期订单 | `OrderRepository.findExpired` | `status + expire_at` |
| 已支付未履约 | `OrderRepository.findPaidUnfulfilled` | `status + paid_at/updated_at` |
| 支付尝试 | `PaymentRepository.findLatestAttempt` | `order_id + created_at` |
| 待处理退款 | `PaymentRepository.findPendingRefunds` | `status + updated_at` |
| 退款重试 | `PaymentRepository.findRetryableRefunds` | `status + next_retry_at` |
| 支付事件 | `PaymentRepository` 幂等查询 | `provider + event_key` |
| 播放日志 | `t_playback_log` 查询 | 用户、视频、事件类型与时间 |
| 管理审计 | `t_admin_audit_log` | 操作人、动作、目标、时间 |

### 方法

1. 在 staging 生成可控数据：先 1 万订单、5 万支付事件、1 万播放日志；不足再增至 10 万。
2. 对每条查询执行 `EXPLAIN FORMAT=JSON` 和 `EXPLAIN ANALYZE`。
3. 记录：使用索引、扫描行数、回表、临时表、filesort、执行时间。
4. 只在有证据时新增或调整索引；新增后复测查询和写入。
5. 临时开启慢查询日志：`long_query_time=0.2`，测试结束关闭，不写进生产配置。
6. 记录 Hikari 指标：活跃连接、空闲连接、等待线程、获取时间。

### 交付物

- `docs/订单链路SQL与索引审计.md`；
- 每条查询的 before/after EXPLAIN 摘要；
- 必要的 Flyway migration（如果确实需要新索引）；
- 连接池结论：10 个连接是否足够、瓶颈在 DB 还是应用。

### 验收

- 核心查询有明确索引依据；
- 新增索引不显著拖慢订单写入；
- 没有为了“看起来专业”而堆冗余索引；
- 压测前没有明显的全表扫描。

## 6. Phase 2：并发、幂等与故障恢复

### 目标

用真实 MySQL 和并发线程验证状态机、唯一键和补偿任务，而不是只验证 mock 对象。

### 测试工具

- JUnit 5 + `CountDownLatch`/`CyclicBarrier` 制造同时起跑；
- Awaitility 等待最终状态，不用固定 `Thread.sleep`；
- Testcontainers MySQL 或独立 staging schema；
- 每个场景至少重复 20 次，避免偶然通过。

### 测试矩阵

| 编号 | 场景 | 关键断言 |
|---|---|---|
| C1 | 同一 `clientRequestId` 并发创建订单 | 只有 1 条订单；所有调用返回同一订单或明确的幂等结果 |
| C2 | 同一订单并发发起支付 | 只有 1 条 PROCESSING 支付尝试；没有重复 `provider_trade_no` |
| C3 | 同一支付事件并发/重复回调 | 只有 1 条事件；订单只履约一次；权益只发一次 |
| C4 | 回调乱序：失败后成功、成功后重复、关闭后成功 | 状态机结果符合策略；不重复发货、不错误退款 |
| C5 | 金额不一致回调 | 订单不发货；异常事件可追踪；不会误确认 |
| C6 | 同一订单并发退款 | 只有 1 条退款；重复请求返回已有退款或明确冲突 |
| C7 | 退款与履约并发 | 终态一致；权益撤销与订单状态不互相覆盖 |
| C8 | 支付成功后、履约前重启 | 重启后补偿任务完成履约，不重复发权益 |
| C9 | 退款 PROCESSING 时重启 | 重启后能查单/重试到终态，不永久卡住 |
| C10 | Redis 不可用时的幂等和限流 | 降级行为明确；数据库唯一键仍能防止重复订单 |

### 已知需要重点验证的风险点

这些是代码审查发现的候选风险，不一定已经复现，测试时优先验证：

1. `PaymentService.pay` 并发时，失败方可能读不到胜方尚未提交的支付尝试，被误报为“支付尝试不存在”。如果复现，考虑短重试、`REQUIRES_NEW` 或把尝试创建与状态迁移做成更原子的写。
2. `RefundService.refund` 并发时，`uk_refund_order` 会阻止重复插入，但第二个请求可能直接收到 `DuplicateKeyException`。应捕获并返回已有退款，或使用条件插入/条件更新。
3. `PaymentConfirmationService` 的事件唯一键能否在事务回滚、重复通知和乱序通知下保持幂等。
4. `OrderFulfillmentService` 的权益发放和订单履约是否真正只发生一次。
5. `OrderService.create` 的 `DuplicateKeyException` 分支在并发下是否能稳定返回同一订单。

### 交付物

- 并发集成测试类；
- `docs/并发与幂等测试矩阵.md`，记录场景、结果、复现步骤和修复；
- 必要的服务层/仓储层修复；
- 一条可在云端执行的测试命令。

### 验收

- 10 个场景全部通过，至少重复 20 次；
- 数据库中没有重复订单、重复权益、重复退款、重复支付尝试；
- 重启后没有永久 `PAYING`、`PAID`、`PROCESSING` 卡死；
- 测试失败时能定位到具体订单号和状态，而不是只看到“偶发失败”。

## 7. Phase 3：JVM/GC 基线与可观测性

### 目标

先建立基线和排障入口，再决定是否调 JVM；不为了“GC 调优”改参数。

### 3.1 GC 日志和 JFR

- staging JVM 增加 GC 日志：

```text
-Xlog:gc*:file=/app/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20M
```

- 只在 staging 增加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/app/logs`，避免生产磁盘被意外占满。
- 空闲、稳定负载、压测中分别采集：
  - `jcmd <pid> VM.flags`
  - `jcmd <pid> GC.heap_info`
  - `jstat -gcutil <pid> 1000 30`
  - `jcmd <pid> Thread.print`
  - `jcmd <pid> JFR.start name=btry-load duration=120s filename=/app/logs/load.jfr`
  - `jcmd <pid> GC.class_histogram`

### 3.2 Prometheus/Grafana

- 新增可选 `compose.observability.yml`，默认不启动，避免长期占用 3.7GB 云主机内存。
- Prometheus 抓取 `backend:9091/actuator/prometheus`；Grafana 只绑定 `127.0.0.1`。
- Prometheus 约 150～300MB、Grafana 约 100～200MB，按镜像和查询量浮动；只在测试窗口启动，结束即停。
- 面板至少包含：
  - JVM 堆/非堆、GC 次数与暂停、线程数；
  - HTTP 请求量、p95/p99、4xx/5xx；
  - Hikari 活跃/空闲/等待连接、获取时间；
  - Redis 调用与降级；
  - 支付创建、成功、失败、重复回调、退款结果；
  - Resilience4j 熔断状态。
- 业务告警继续复用应用内 `AlertPublisher`；没有真实 webhook 和值班流程时，不额外引入 Alertmanager。

### 3.3 JVM 结论

只有出现下列证据才考虑调参：

- 频繁 Full GC 或长时间停顿；
- 堆持续上涨且 Full GC 后不回收；
- 线程数持续增长；
- Hikari 等待严重但 DB 不忙；
- 外部调用超时导致线程堆积。

### 交付物

- `docs/JVM与GC基线报告.md`；
- `compose.observability.yml`、Grafana provisioning 和 dashboard JSON；
- `docs/监控面板与告警.md`；
- 空闲/负载两套指标摘要。

### 验收

- 30 分钟稳定负载下无 OOM、无 Full GC 风暴；
- 压测后堆能回落到基线附近；
- 线程数稳定，Hikari 等待可解释；
- 面板能在一个页面看到 JVM、HTTP、DB 和支付指标；
- 不启动 observability profile 时，staging 资源占用不增加。

## 8. Phase 4：k6 压测与容量结论

### 目标

测“控制面”而不是视频字节：登录、学习空间、播放地址、订单创建、订单详情。视频仍然由浏览器直连 COS，不经过服务器 3M 带宽。

### 场景

k6 是单文件二进制，不依赖本地 Docker，可在云端临时安装；压测结束删除测试数据并停止进程。

| 场景 | 接口 | 说明 |
|---|---|---|
| 登录 | `POST /api/auth/login` | 单独低并发，避免登录限流污染结果 |
| 学习空间 | `GET /api/learning/series` | 预登录 token，避免每轮登录 |
| 系列详情 | `GET /api/learning/series/{id}` | 预登录 token |
| 播放地址 | `GET /api/learning/videos/{id}/play` | 只测预签名和缓存，不下载视频 |
| 创建订单 | `POST /api/orders` | Mock 支付；使用唯一 clientRequestId |
| 订单详情 | `GET /api/orders/{orderNo}` | 预创建订单 |

### 负载阶梯

| 阶段 | 并发 | 时长 | 目的 |
|---|---:|---:|---|
| smoke | 1 VU | 1 分钟 | 脚本正确性 |
| baseline | 10 VU | 3 分钟 | 建立基线 |
| step-1 | 50 VU | 5 分钟 | 观察连接池和 GC |
| step-2 | 100 VU | 5 分钟 | 找到第一处瓶颈 |
| step-3 | 200 VU | 5 分钟 | 验证拐点，不稳定就停止 |

如果 200 VU 仍稳定，再考虑 300 VU；不预设“必须支持多少人”。

### 初始验收阈值

阈值用于发现异常，不是营销数字；首轮后按实际基线调整：

- 错误率 < 1%；
- 读接口 p95 < 300ms、p99 < 800ms；
- 创建订单 p95 < 800ms、p99 < 2s；
- Hikari pending 持续为 0，active 不超过池大小的 80%；
- GC p99 暂停 < 200ms，无 Full GC 风暴；
- 应用 CPU 不持续打满，无 OOM。

### 采集

- k6 summary JSON；
- Prometheus 快照；
- `docker stats`；
- `jstat`、`jcmd GC.heap_info`；
- MySQL `SHOW GLOBAL STATUS`、`SHOW PROCESSLIST`、慢查询日志。

### 重要说明

- “100 个学生同时看视频”不等于 100 个请求持续打到后端；后端主要处理列表、播放地址、进度和日志。
- 压测只测后端控制面，不把 COS 下行带宽算进服务器瓶颈。
- 在云服务器本机跑 k6 会与应用争抢 CPU；结论按“方向性”使用，有条件时再用独立压测机复测。
- 登录和下单都有限流，压测应使用预登录 token、账号池或独立测试配置，不能关闭生产限流。

### 交付物

- `tools/k6/` 脚本；
- `docs/压测报告.md`；
- 瓶颈结论：在哪个并发级别、哪个资源先饱和、下一步该改什么；
- 压测后清理脚本和 staging 恢复说明。

### 验收

- 至少完成 smoke、baseline、50、100 四档；
- 报告能回答“瓶颈在应用、DB、连接池还是 GC”；
- 每次调优都有 before/after，而不是只改参数；
- 压测结束停止 k6、observability 和 staging，生产不受影响。

## 9. Phase 5：OpenTelemetry 链路追踪（可选）

### 目标

只解决“支付回调、查单、退款、COS 预签名出问题时怎么定位”，不做全量方法追踪。

### 方案

优先尝试 Spring Boot 原生方案：

- `io.micrometer:micrometer-tracing-bridge-otel`
- `io.opentelemetry:opentelemetry-exporter-otlp`
- staging 用 Jaeger all-in-one 接收 OTLP；
- 生产默认关闭或低采样，只有配置了 collector 才启用。

实施前先确认 Spring Boot 3.3 的 OTLP tracing 自动配置属性；如果不满足，再改用 OpenTelemetry Java Agent，不为了“纯代码接入”增加复杂度。

### 需要埋点的位置

- 支付宝回调入口；
- 支付发起、主动查单、退款；
- 补偿任务中的订单/退款处理；
- COS 预签名和播放 URL 缓存；
- 关键的 JDBC/Redis 调用由自动 instrumentation 覆盖。

### 关联字段

- `traceId`：日志 MDC、支付事件、审计日志；
- `orderNo`、`attemptNo`、`providerTradeNo`、`refundNo`；
- `videoId`、`cache.hit`、`payment.channel`、`event.type`。

不记录密钥、完整回调报文、手机号等敏感信息。

### 交付物

- 依赖和配置；
- 关键 span；
- `docs/链路追踪接入与排障.md`；
- 一条 Mock 支付的完整 trace 截图/导出。

### 验收

- 一次支付能串起 HTTP → 服务 → DB → 外部调用；
- 日志里的 traceId 与 trace 一致；
- 采样率可配置；
- 关闭 tracing 后应用行为和测试不受影响。

## 10. Phase 6：文档与收尾

- 更新 `docs/生产运维手册.md`：GC 日志、面板、压测入口、故障排查。
- 更新 `docs/Docker运行与云服务器验证.md`：observability profile、k6、报告目录。
- 清理 staging 测试数据，停止 observability 和 k6。
- 把原始 JFR、heap dump、k6 结果放到 `reports/`，不提交大文件。
- 在 README 增加“工程验证”入口，不写空泛技术栈。

## 11. 时间不够时的最小方案

如果只能投入 3 天，建议保留：

1. 并发/幂等/故障恢复测试（P0，1.5～2 天）；
2. SQL/索引审计（P0，0.5 天）；
3. 一次 smoke + baseline 压测和 JVM 基线（P0，0.5～1 天）。

暂时不做：

- Grafana 面板；
- OpenTelemetry；
- 200 VU 以上压测；
- JVM 参数调优。

这仍然能形成一套可信的“稳定性 + 数据库 + 并发”证据链，而且不会为了展示增加无用组件。

## 12. 明确不做

- 不引入 CDN、HLS、MQ/outbox、Kubernetes、Spring Cloud/微服务；
- 不为了压测关闭生产限流；
- 不对生产库做破坏性并发测试；
- 不在没有基线数据时修改 G1 参数；
- 不把 Grafana/Jaeger 暴露到公网；
- 不用真实支付宝扣款做压测；
- 不把“500 并发”当成目标数字，容量以实测瓶颈为准。

## 13. 退出标准

全部完成后，应能拿出以下证据：

- 并发场景重复 20 次通过，数据库无重复订单/权益/退款；
- 支付中、退款中重启后能自动恢复；
- 核心 SQL 有 EXPLAIN 和索引依据；
- 有 GC/JFR 基线和压测报告；
- 有 JVM、HTTP、Hikari、支付指标面板；
- 有至少一条支付链路的完整 trace（如果做了 Phase 5）；
- 生产 systemd 未受影响，staging 可一键停止；
- 文档能说明“为什么这样做、怎么复现、失败时看哪里”。
