## 一、项目与目标

- `atry`：原始完整项目样本，保留不动。
- `btry`：当前改造项目，目标是学生登录后进入学习空间，选择系列，按章节顺序观看录播视频。
- 当前视频只是占位样本，实际视频预估为 10～40 分钟。
- 明确不使用 CDN。
- 明确不使用云服务器传输视频字节。
- 视频字节始终由浏览器直接访问 COS。
- 云服务器即使以后部署，也只承担 API、登录、播放地址签发等轻量请求。
- 暂时不提供其他 MP4 样本。

## 三、确定的技术结论

### CDN

- 不使用 CDN。
- 100 人同时观看本身不是上 CDN 的理由。
- COS 中国大陆单账号单地域默认上下行各 15 Gbit/s。
- 单文件下载热点默认 1000 QPS，每桶读请求 30000 QPS。
- 当前 0.65 Mbps 视频，100 人约 65 Mbps。
- CDN 只作为成本、跨地区延迟等未来选项，不在当前范围。

### HLS 与分段缓存

- HLS：把视频切成小段，适合长视频、多码率、精细拖动。
- 分段缓存：缓存 HLS 小段或部分区间。
- 没有 CDN 时，分段缓存只在本机生效，不能跨用户共享。
- 当前 3 分钟样本不适合 HLS。
- 10～40 分钟真实视频是否值得 HLS，需要真实拖动数据和成本数据。
- 当前不实现 HLS，不实现分段缓存。

### 视频并发

- 100 人同时观看：COS 直连带宽和官方配额足够。
- 之前的 500/1000 是短 Range 请求并发测试，不等同于 500/1000 个真实浏览器会话。
- 真实 500 人测试需要多台机器、多网络环境和真实播放器。
- 该测试只用于验证 COS 直连边界，不用于决定 CDN。

## 四、Java 技术深度讨论

当前 `btry` 视频部分：

- 没有 AOP。
- 没有自定义注解。
- 没有 Redis。
- 没有 MyBatis。
- Java 深度中等偏浅。
- 现有亮点：COS 预签名、URL TTL 缓存、进程内原子填充、URL 过期恢复、日志入库、保留策略、统计视图。

提出的“技术深度版”：

- Redis：分布式 URL 缓存、单飞锁、TTL 抖动、限流、热 key 处理。
- AOP + 自定义注解：播放审计、限流、指标、幂等。
- MyBatis：动态日志查询、批量插入、统计聚合。
- 异步日志：有界队列、批量写库、背压和降级。
- Resilience4j：COS 超时、重试、熔断。
- Micrometer + Actuator：缓存命中率、错误率、p95/p99。
- 测试：TTL、缓存击穿、单飞、URL 过期、COS 失败注入。

这些是“技术深度”方向，不代表全部必须立即实现。
